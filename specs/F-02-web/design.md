# F-02-web — Diseño

## Resumen

Se construyen las pantallas de **recepción** (bandeja de pre-registros con confirmación y rechazo, y registro directo con búsqueda y alta de paciente, incluido NN) y la **consulta de atenciones** (lista filtrable y detalle con línea de tiempo), más la **cancelación** de una atención por `RECEPTION` o `NURSE`. La web nunca envía horas: `arrivalAt` la fija la API al confirmar o registrar (ADR 0008, F-02.AC3) y la web solo la muestra en America/Bogota.

## Impacto en contrato

- **Sin cambios en el contrato.** La web pasa de consumir 0.2.1 a **consumir 0.4.0** (`info.version` de `../asclepio-api/openapi/asclepio-api.v1.json`).
- Endpoints que usa (roles según `../asclepio-api/specs/F-02-api/design.md`):
  - `GET /api/v1/public/tenants` (público) → 200 `PublicTenantDto[]`; 429 con `Retry-After`; `default` problem+json.
  - `GET /api/v1/pre-registrations?siteId` (RECEPTION) → 200 `PendingPreRegistrationDto[]`; 400, 401, 403.
  - `POST /api/v1/pre-registrations/{id}/confirm` (RECEPTION) — `ConfirmPreRegistrationDto { identityVerified: true }` → 201 `EncounterDto`; 404, 409 (no vigente o atención activa), 422.
  - `POST /api/v1/pre-registrations/{id}/reject` (RECEPTION) — `RejectPreRegistrationDto { reason }` → 200 `RejectedPreRegistrationDto`; 400, 404, 409.
  - `GET /api/v1/patients?documentType&documentNumber` (RECEPTION) → 200 `PatientDto[]` (0 o 1); 400.
  - `POST /api/v1/patients` (RECEPTION) — `CreatePatientDto` → 201 `PatientDto`; 400 con `errors[]`, 409 (documento repetido), 422 (fecha futura).
  - `POST /api/v1/encounters` (RECEPTION) — `CreateEncounterDto { patientId, siteId, chiefComplaintText, complaintSource }` → 201 `EncounterDto`; 400, 409 (pre-registro vigente o atención activa), 422 (paciente o sede ajenos).
  - `GET /api/v1/encounters?status&siteId&limit&offset` (cuatro roles) → 200 `EncounterListDto`. La web no usa el filtro `patientId`.
  - `GET /api/v1/encounters/{id}` (cuatro roles) → 200 `EncounterDto` con `events`; 404.
  - `POST /api/v1/encounters/{id}/cancel` (RECEPTION, NURSE) — `CancelEncounterDto { reason }` → 200 `EncounterDto`; 400, 404, 409.
- No usa: `/patient/*` (móvil), `/encounters/{id}/vital-signs|symptom-findings|clinical-capture` (F-03-web). Los tipos de evento de F-03 solo se etiquetan en la línea de tiempo.
- **Regeneración de tipos:** `npm run api:types` regenera `src/shared/api/schema.d.ts` desde el snapshot 0.4.0; `CONSUMED_CONTRACT` pasa a `'0.4.0'`; los tipos de la UI se derivan de `components['schemas']`. El `leader` fija `consumes_contract: "0.4.0"` en `feature_list.json` (C8).

## Impacto en datos

Sin impacto en datos. La web no tiene base de datos ni guarda nada nuevo en el navegador: los datos de F-02 viven solo en la caché en memoria de TanStack Query, que se vacía al cerrar sesión (F-01-web).

## Riesgos y pruebas

**Riesgos**

- Dos recepcionistas confirman el mismo pre-registro: la API garantiza un único 201 (R20 de F-02-api); la web muestra el 409 en contexto y refresca la bandeja (R13).
- Pre-registro que expira entre dos refrescos: la confirmación da 409 y la bandeja se refresca (R13).
- Fecha de nacimiento desplazada un día por la zona horaria: cubierto por D10 y su prueba.
- Fuga de datos personales en URL o consola: R40 con prueba transversal.
- Cambio de la prueba de R23 de F-01-web para `RECEPTION` (D4): se ajusta en la misma tarea que cambia la ruta.

**Pruebas (Vitest + Testing Library, nombres `R<n>: …`)**

- Unitarias: `formatCivilDate` y `formatBogota` con horas UTC fijas (R39); `actionErrorMessage` y `applyFieldErrors` (R13, R16, R23, R27, R36); esquemas Zod y `toCreatePatientBody` (R15, R18, R20–R22, R25, R35); `canAccess` con subrutas (R1).
- Componentes con red simulada (`fakeApi`) y `createMemoryRouter(routes)`: acceso por cada rol a las cuatro rutas (R1, R2); sedes (R4, R5); bandeja con filtro, estados y refresco con temporizadores falsos (R6–R9); confirmación y rechazo con 201/200/409/404/403/red (R10–R16); registro directo completo con documento y NN (R17–R27); lista, paginación y detalle con línea de tiempo y 404 (R28–R33); cancelación por rol y estado (R34–R36); doble envío (R37).
- Cuerpos y queries exactos registrados por `fakeApi` en cada petición (R11, R16, R19, R22, R26, R28, R36, R38).
- Privacidad (R40): espías en `console.*` y `location.pathname/search/hash` tras confirmar, rechazar, buscar, crear, registrar y cancelar.
- Manual: flujo real contra la API local (pre-registro desde la app o `curl`, confirmación, rechazo, registro directo con documento y NN, consulta y cancelación) con usuarios de los cuatro roles, en escritorio y en ancho de tablet (RNF-13); registro en `progress/impl_F-02-web.md`.
