# F-03-web — Dashboard de enfermería y captura clínica

Brief global: `../asclepio-api/docs/product/features/F-03.md` (F-03.AC1–AC5, PA-F03-1–4 resueltas).
Decisiones de interfaz autorizadas: `docs/f03-brief.md` (plan aprobado expresamente por el usuario el 2026-10-28); continuidad visual/accesible: `docs/ui-migration.md` (UI-01.AC1–AC8).
Contrato: consume **0.4.0**; F-03-api `done`; solo lectura de contrato y API.
RNF aplicables: RNF-01, RNF-02, RNF-05, RNF-10, RNF-11, RNF-12, RNF-13, RNF-14, RNF-15, RNF-18. Auditoría e inmutabilidad las garantiza la API: la web muestra sus resultados, sin escribir eventos ni atribuirse esa responsabilidad.

Glosario: **captura** = una toma o un lote de hallazgos enviados por separado; **estado habilitado** = atención actual en `WAITING_TRIAGE`; **datos clínicos** = valores de signos, descripciones, motivo y datos personales; **reglas publicadas** = tabla de `design.md`, procedente de PA-F03-1–4 y del contrato 0.4.0, provisional y no validada clínicamente. La numeración R pertenece a este slice.

## Requisitos

- **R1** (Ubicuo) El sistema deberá permitir `/triage` y `/triage/:id` solo a `NURSE`, conservando los guards actuales y sin solicitar datos de esas vistas cuando el rol no esté autorizado. (→ F-03.AC1, F-03.AC5; RNF-12)
- **R2** (Por evento) Cuando se abra la bandeja o cambien sus filtros, el sistema deberá pedir `GET /api/v1/encounters` con `status=WAITING_TRIAGE`, `limit=50`, `offset` y `siteId` solo si hay una sede elegida, conservar sede/offset en la URL y reiniciar offset a 0 al cambiar sede. (→ F-03.AC1, F-03.AC5)
- **R3** (Ubicuo) El sistema deberá mostrar en la bandeja paciente, documento si existe, sede, hora de llegada del servidor y enlace de captura por atención, con opciones de sede del tenant, paginación de 50 y botón de actualización manual, sin temporizador ni KPI nuevos. (→ F-03.AC1, F-03.AC5; UI-01.AC2)
- **R4** (Por estado) Mientras una consulta de bandeja, contexto o historial esté cargando, vacía o fallida, el sistema deberá mostrar su estado explícito con `status`/`alert` y reintento manual cuando corresponda, sin presentar datos de una consulta fallida o de otra atención como actuales. (→ F-03.AC5; UI-01.AC6)
- **R5** (Por evento) Cuando se abra `/triage/:id`, el sistema deberá cargar el contexto y captura de esa atención, mostrar paciente, sede, estado y motivo original literal, y montar formularios/historial propios de ese id para descartar los borradores y avisos de otra atención. (→ F-03.AC1, F-03.AC3, F-03.AC5)
- **R6** (Por evento) Cuando `NURSE` o `PHYSICIAN` abra `/atenciones/:id`, el sistema deberá ofrecer el historial clínico solo lectura y, para `NURSE` en estado habilitado, un enlace de captura; para `RECEPTION` o `ADMIN` deberá conservar el detalle existente sin renderizar ni solicitar `/clinical-capture`. (→ F-03.AC1, F-03.AC3, F-03.AC5; RNF-12)
- **R7** (Ubicuo) El sistema deberá ofrecer en una toma los siete signos obligatorios y dos opcionales publicados con etiqueta/unidad, oxígeno suplementario sí/no y conciencia A/C/V/P/U sin selección inicial, identificando los opcionales y el carácter provisional de las reglas. (→ F-03.AC1, F-03.AC2, F-03.AC5)
- **R8** (No deseado) Si una toma incumple obligatoriedad, tipo, dominio, límites inclusivos, precisión o coherencia sistólica/diastólica de las reglas publicadas, entonces el sistema deberá impedir su POST mediante Zod, mostrar errores asociados a los campos y enfocar el primer campo inválido. (→ F-03.AC2, F-03.AC5)
- **R9** (Por evento) Cuando se envíe una toma válida, el sistema deberá omitir los opcionales vacíos, conservar los números y el valor booleano falso válidos, y llamar a `POST /api/v1/encounters/{id}/vital-signs` con únicamente los signos permitidos. (→ F-03.AC1, F-03.AC2, F-03.AC5)
- **R10** (Por estado) Mientras un formulario esté enviando una captura, el sistema deberá impedir el doble envío de ese formulario y realizar una sola petición sin reintento automático ni campos de hora, responsable, tenant o identificadores dentro del cuerpo. (→ F-03.AC1, F-03.AC3, F-03.AC5; RNF-10, RNF-14)
- **R11** (Por evento) Cuando enfermería prepare hallazgos, el sistema deberá permitir añadir y quitar filas antes del envío y validar con Zod entre 1 y 20 filas, cada una con `kind` SYMPTOM/FINDING/COMPLAINT_NOTE y `description` de 1–500 caracteres tras quitar espacios extremos, enviando solo `{ items }` a `POST /api/v1/encounters/{id}/symptom-findings` si el lote es válido. (→ F-03.AC3, F-03.AC5)
- **R12** (Ubicuo) El sistema deberá mantener el motivo original como solo lectura y registrar las precisiones de enfermería únicamente como nuevos hallazgos COMPLAINT_NOTE, sin ofrecer una operación de modificación del motivo. (→ F-03.AC3, F-03.AC5; PA-F03-4)
- **R13** (Por evento) Cuando una captura responda 201, el sistema deberá mostrar éxito, limpiar únicamente el formulario enviado y refrescar captura, detalle con eventos y lista de atenciones, conservando el borrador del otro formulario y sin insertar registros optimistas. (→ F-03.AC1, F-03.AC3, F-03.AC4, F-03.AC5)
- **R14** (Ubicuo) El sistema deberá mostrar todas las tomas y hallazgos guardados en el orden ascendente de `recordedAt` e id recibido de la API, con sus valores literales, unidades, fecha/hora del servidor en `America/Bogota` y responsable, sin controles para editar o borrar registros. (→ F-03.AC1, F-03.AC3, F-03.AC4, F-03.AC5; RNF-02, RNF-10)
- **R15** (Por estado) Mientras la atención no esté en `WAITING_TRIAGE`, el sistema deberá mantener disponible su consulta autorizada e impedir el envío de ambos formularios de captura. (→ F-03.AC1, F-03.AC3, F-03.AC5)
- **R16** (No deseado) Si un POST responde 400 o 422 con `errors[]`, entonces el sistema deberá asociar los campos reconocidos a sus controles con errores localizados y accesibles, mostrar un error de acción para campos no reconocidos y conservar todo el borrador. (→ F-03.AC2, F-03.AC3, F-03.AC5; UI-01.AC3)
- **R17** (No deseado) Si un POST responde 409, entonces el sistema deberá mostrar el conflicto en contexto y refrescar captura, detalle/estado y bandeja, impedir nuevos envíos durante esa comprobación y mantenerlos bloqueados si la atención ya no está en espera, sin perder el borrador. (→ F-03.AC1, F-03.AC3, F-03.AC5)
- **R18** (No deseado) Si una captura falla por red u otro error no tratado, entonces el sistema deberá mostrar el error de acción traducido y conservar el borrador sin reintentar automáticamente el POST. (→ F-03.AC1, F-03.AC3, F-03.AC5; UI-01.AC3)
- **R19** (No deseado) Si una petición de F-03 recibe 401, 403 o 404, entonces el sistema deberá aplicar respectivamente el cierre de sesión vigente y login, la vista sin permiso o la vista de atención no encontrada, sin mostrar resultados clínicos anteriores como vigentes. (→ F-03.AC1, F-03.AC3, F-03.AC5; RNF-12)
- **R20** (Ubicuo) El sistema deberá mantener borradores clínicos solo en memoria, excluir datos clínicos de almacenamiento persistente, URL, logs y guía de voz, y obtener los tipos API del snapshot 0.4.0 mediante el cliente HTTP central. (→ F-03.AC1, F-03.AC3, F-03.AC5; UI-01.AC8; RNF-05, RNF-14)
- **R21** (Ubicuo) El sistema deberá reproducir la composición, geometría, espaciado, tokens, fuentes e iconos del NurseView, VitalSignsForm y RoleDashboardShell de `develop` anterior para los elementos equivalentes, adaptando únicamente contenido y operaciones al contrato/roles vigentes y usando los componentes actuales. (→ F-03.AC5; UI-01.AC1, UI-01.AC2)
- **R22** (Ubicuo) El sistema deberá traducir interfaz, validaciones, errores controlados y ARIA del nuevo flujo a es/en/pt/fr/de, conservando literalmente nombres, documentos, motivo y descripciones clínicas recibidas o escritas. (→ F-03.AC5; UI-01.AC3)
- **R23** (Por evento) Cuando cambien idioma, tema o preferencias accesibles, el sistema deberá actualizar el flujo sin recarga ni pérdida de borradores y mantener controles operables con teclado, foco visible y sin cortes a 375/768/1024/1440 px, zoom 200 % y movimiento reducido. (→ F-03.AC5; UI-01.AC3, UI-01.AC4, UI-01.AC7; RNF-13)
- **R24** (Por evento) Cuando cambien ruta, idioma o texto de la guía, el sistema deberá cancelar la narración, descartar callbacks anteriores y comenzar inactivo y sin error incluso tras A→B→A, ofreciendo para las nuevas rutas solo instrucciones estáticas activadas explícitamente y sin bloquear el flujo si la síntesis no está disponible. (→ F-03.AC5; UI-01.AC5)

## Preguntas abiertas

Ninguna decisión de producto pendiente. PA-F03-1–4 ya están resueltas en la API y se trasladan sin alterar sus valores provisionales. La integración con API real requiere configuración local del equipo; su ausencia se documenta como limitación de verificación autorizada, no como una nueva regla clínica.
