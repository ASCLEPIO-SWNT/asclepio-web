# F-06-web — Diseño

> Este diseño aplica PA-1..PA-12 con la opción (a), que el humano eligió en cada una el 2026-11-10.

## Resumen

`/cola` deja de ser el dashboard de UI-02-web (tres `GET /encounters` de conteo, «Atenciones recientes» y la franja «pendiente») y pasa a mostrar la **cola priorizada** de `GET /api/v1/queue` (PA-1 a). Se conservan el encabezado («Cola priorizada» y «Actualizar») y la barra de resumen. Sus tres cifras salen ahora de las secciones de la misma respuesta, y suma el filtro «Sede». Debajo van las tres secciones («En espera de triage», «Clasificadas», «En atención») en el orden que entrega la API, con iniciales, edad, sexo, nivel final, llegada, espera, tiempo máximo y la alerta de tiempo superado. La cola se refresca cada 30 s con la pestaña visible. Para PHYSICIAN, cada fila de «Clasificadas» tiene «Iniciar atención» y cada una de «En atención», «Cerrar atención», con confirmación previa.

## Impacto en contrato

- Consume **0.7.0** (antes 0.6.0):
  - `GET /api/v1/queue?siteId=<uuid>` (`PHYSICIAN`, `NURSE`, `ADMIN`) → **200** `QueueDto { serverNow, waitingTriage, triaged, inCare }` con `QueueItemDto { encounterId, siteId, siteName, status, finalLevel, arrivalAt, waitMinutes, maxWaitMinutes, overdue, patient: QueuePatientDto { initials, ageYears, sex } }`. **400** (`siteId` no UUID o parámetro desconocido: la web solo envía UUID de `useSites`) · **401** · **403**. Sede de otro tenant o inexistente → 200 con secciones vacías.
  - `POST /api/v1/encounters/{id}/start-care` y `POST /api/v1/encounters/{id}/close` (`PHYSICIAN`), sin cuerpo → **200** `EncounterDto` (la web no lo usa más allá del éxito) · **400** · **401** · **403** · **404** · **409**. Todas las respuestas de error en `application/problem+json`.
- Tipos: `npm run api:types` sin diff (el snapshot ya es 0.7.0). Alias nuevos en `client.ts`: `Queue`, `QueueItem`, `QueuePatient`. Ningún tipo escrito a mano.
- `CONSUMED_CONTRACT` y `EXPECTED_CONTRACT`: `'0.6.0'` → `'0.7.0'`. `feature_list.json` ya declara `consumes_contract: "0.7.0"`.
- La web no cambia el contrato.

## Impacto en datos

Sin impacto en datos: la web no tiene base de datos ni migraciones. La cola vive solo en la caché de TanStack Query, y nada se escribe en `localStorage`, `sessionStorage` ni en la URL (D14). Las transiciones las registra la API en `encounter_events` y `audit_log` (F-06-api R9, R10). La web no envía horas (R19, RNF-10).

## Riesgos y pruebas

**Riesgos**

- (1) Acción irreversible: un toque equivocado sacaría a un paciente de la espera. Se mitiga con la confirmación con iniciales y nivel (PA-9 a), y con el 409 de la API ante cambios concurrentes.
- (2) Datos de hasta 30 s: la espera no avanza entre respuestas (PA-5 a). Se mitiga con la hora de la cola visible y, si falla un refresco, con el aviso con la hora de los datos (PA-6 a).
- (3) Dos médicos sobre la misma fila: uno recibe 409 y la cola se vuelve a leer (D11). Lo cubre la verificación manual con dos pestañas.
- (4) Cambio de sede durante un refresco: la clave cambia y la respuesta antigua no se pinta (D3).
- (5) Muchas pruebas de UI-02-web atadas al dashboard antiguo: la lista de arriba es cerrada.

**Integración** (`renderApp` + `fakeApi`, en `src/app/router/f06Routes.test.tsx` bajo `describe('F-06-web …')`):
